一、智能客服主流程（flowchart）

flowchart TD
    A(["用户发起咨询"]) --> B["渠道接入：网页 / App / 微信服务号"]
    B --> C["建立会话并落库"]
    C --> D{"意图识别"}
    D -->|订单物流| E["调用订单查询接口"]
    D -->|退换货| F["走售后工单流程"]
    D -->|产品咨询| G["检索知识库"]
    D -->|置信度低| H["反问澄清"]
    H --> C
    E --> I["组装结构化答案"]
    G --> J["混合召回 + 精排取 Top-K"]
    J --> K["大模型生成答案并附引用"]
    I --> L{"答案置信度达标"}
    K --> L
    F --> L
    L -->|达标| M(["返回答案给用户"])
    L -->|不达标或负向情绪| N["转人工坐席"]
    N --> O["结束会话并生成工单"]
    O --> P["人工结论回补知识库"]
    P --> G
    M --> Q(["记录埋点与用户评价"])
    Q --> R["样本进评测集"]

读法：从顶部用户发起咨询往下走，菱形是判断节点。注意两条往回的箭头—— 一条是「反问澄清」回到会话继续识别，另一条是「人工结论回补知识库」回到检索， 这两条环让系统能越用越准，也是流程图比截图更能说清逻辑的地方。

二、会话与知识库的实体关系（erDiagram）

erDiagram
    USER ||--o{ SESSION : "发起"
    SESSION ||--|{ MESSAGE : "包含"
    SESSION ||--o| TICKET : "生成"
    AGENT ||--o{ SESSION : "接管"
    AGENT ||--o{ TICKET : "处理"
    INTENT ||--o{ MESSAGE : "归类"
    DOCUMENT ||--|{ CHUNK : "切分为"
    CHUNK ||--o{ CITATION : "被引用"
    MESSAGE ||--o{ CITATION : "附带"
    TICKET }o--o{ DOCUMENT : "沉淀"

    USER {
        bigint id PK "主键"
        varchar nickname "昵称"
        varchar channel "来源渠道"
        datetime created_at "注册时间"
    }

    SESSION {
        bigint id PK "主键"
        bigint user_id FK "所属用户"
        bigint agent_id FK "接管坐席"
        tinyint status "0会话中 1已结束"
        datetime started_at "开始时间"
    }

    MESSAGE {
        bigint id PK "主键"
        bigint session_id FK "所属会话"
        bigint intent_id FK "识别出的意图"
        varchar role "user 或 bot"
        text content "消息正文"
        float confidence "置信度"
    }

    INTENT {
        bigint id PK "主键"
        varchar name "意图名称"
        varchar route "命中后走的流程"
    }

    DOCUMENT {
        bigint id PK "主键"
        varchar title "文档标题"
        varchar source "来源系统"
        datetime updated_at "最后更新时间"
    }

    CHUNK {
        bigint id PK "主键"
        bigint document_id FK "所属文档"
        text content "片段正文"
        int tokens "token 数"
        int version "版本号"
    }

    CITATION {
        bigint id PK "主键"
        bigint message_id FK "哪条回答"
        bigint chunk_id FK "引用的片段"
        float score "相关度得分"
    }

    AGENT {
        bigint id PK "主键"
        varchar name "坐席姓名"
        varchar team "所属组"
        tinyint online "是否在线"
    }

    TICKET {
        bigint id PK "主键"
        bigint session_id FK "来源会话"
        bigint agent_id FK "处理坐席"
        tinyint status "工单状态"
        text conclusion "处理结论"
    }

读法：||--o{ 读作「一 对 零或多」，||--|{ 是「一 对 一或多」， }o--o{ 是「多 对 多」。所以 USER 到 SESSION 是一对多， 而 TICKET 与 DOCUMENT 因为一个工单可能涉及多篇文档、一篇文档也可能被多个工单引用，所以是多对多。 外键靠 FK 标注，主键靠 PK，这就是画 ER 图时最该先定的两件事。

mermaid 是怎么把文字变成图的

1. 写在 pre 里，不是写在图里 <pre class="mermaid"> 里面就是纯文本 DSL。 mermaid 找到这个元素，读走里面的文本，解析成语法树，再往页面里插一段 SVG。 所以图里的每一个框，本质上都是一个 <text> 加几个矩形。
2. 三种图对应三种 DSL 开头 第一行的关键字决定图型：flowchart TD 是自上而下的流程图， erDiagram 是实体关系图，还有 sequenceDiagram、 gantt、classDiagram 等等，写法互不相同。
3. 布局是自动算的，这点和手画相反 不用管坐标，只表达「谁连谁」，节点位置交给它的布局算法。 代价是不能像素级微调，好处是流程改一条线，整张图自己重排，不会像截图那样对不上。
为什么必须用本地 cdn mermaid 官方推荐的是 <script type="module"> 引 CDN， 但模块脚本在 file:// 下会被 CORS 拦掉。 这里下载的是 UMD 版 mermaid.min.js，用普通 <script> 引入，双击打开就能用。
